## install · 0.2.0 · 2026-10-24 — the client register is seeded from one template, and a place that cannot say whose client it is is a red

### Why
Plan 128, phases 2 and 3. The installer carried TWO sources of one truth: registry/projects.yaml.example and an inline heredoc that rewrote projects.yaml at the tree step — two things that drift by construction, and the heredoc also re-seeded a register the operator had edited. There was no clients shelf at all, so a company the house SERVES had nowhere to live and was filed as a house (the fault that made the plan necessary). Now: one template per fact in registry/ (clients.yaml.example, companies.yaml.example, projects.yaml.example) and the installer COPIES, never writes YAML inline. A new clients step seeds hodd/identity/{clients,companies}.yaml when absent and then reads the ONE door that already decided the relation — bin/identity/place-validate.sh --all — so the install and the operator can never disagree: a place whose client_of names no resolvable house, or a place that declares client_of beside no register at all, is a FAIL row naming the file and the fix, and the install exits 1. Absent is a red, not a shrug. Proven by .agents/tests/clients-register.test.sh (27 checks, including the install --check red and the migration's idempotence).

### Also
The copy itself is one door, `bin/identity/registers-seed.sh` (`--check` writes nothing, an existing register is never touched): the `clients` step calls it instead of carrying the loop, so a human can seed a home's registers the same way the installer does, and the proof exercises the same code the install runs. `--check` on the installer still reports the register's absence as a WARN when there is nothing to resolve, and as a FAIL the moment a place declares a `client_of` that cannot be resolved.
