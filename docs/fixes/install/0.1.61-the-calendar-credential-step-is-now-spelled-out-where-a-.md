## install · 0.1.61 · 2026-10-01 — the calendar credential step is spelled out where a user meets it

### Why
The Allfather, mid-consent: *"what am i doing in the google workspace credentials? this must be
clear in the updates and installlations for ymir."*

He was right, and the gap was real. Plan 60 settled the **law** — Ymir is single-user per
install, the calendar is the operator's, the grant lives in **their own** `ymirhome` — but the
**Connect door** that was supposed to make it a button (`/api/calendar/connect|callback` plus
`hodd.sh set`) **was never built**. So the only way to do it today is to hand-edit an
age-encrypted vault, with the reasoning nowhere on the machine.

Three facts a user cannot guess, and each has cost somebody a wrong turn:

- **An API key cannot do this.** `GOOGLE_API_KEY` names an application; a person's calendar
  needs OAuth, where the person consents once and Ymir holds a refresh token instead of a
  password.
- **The client type is load-bearing.** Only a **Desktop app** client accepts a loopback
  callback. The only Google client on this seat is the Way of Teams **web** client with a
  **hosted** redirect — a web client's registered URI is enforced exactly, so borrowing it sends
  the code *to that product*, which is how a calendar grant ends up in a customer-facing system
  instead of the user's own vault.
- **A new client is in testing mode** and refuses any account not listed under **Test users**,
  so "Sign in with Google" fails for everyone else — by design, and it reads as a fault.

### Fix
- **`bin/engine/ymir-install.sh` now prints the whole step, and only when the grant is absent** — the
  five steps in order, the scope, the test-user rule, where the values go
  (`hodd/secrets/platform.env`), and how to confirm they arrived. It is **never a FAIL**: the
  hall is fully usable without it, and the grid says *"the reckoning is not granted"* until it
  is done. A door that fails on a missing optional key teaches people to ignore doors.
- **The installation asset carries the reasoning**, including *why* each step is what it is and
  what is deliberately absent: no service account, no domain-wide delegation, no shared
  calendar, no token held for anyone else. Those are different products with different blast
  radii.
- It also states the honest debt: **the Connect door is not built**, so these steps are manual
  today and this section is the substitute — not a claim that the button exists.

### Verified

- `bin/gates/guards.sh` PASS (including `defaults-guard`, which refuses a literal `$HOME/…` home — the
  installer resolves the vault through its own door).
