## gate · 0.2.1 · 2026-11-03 — One door for every generated register

### Why
Two registers, two generators, two gates and almost the same name: a change that adds a door regenerates the one it remembers and goes red in CI only. bin/gates/registers.sh owns the list, a seated ward calls it, so a push and CI judge the same set.

### Files
- `bin/gates/registers.sh`
- `bin/gates/guards/registers-guard.sh`
- `bin/gates/guards.sh`
- `bin/gates/tests/test_registers.sh`
- `docs/features/one-door-for-the-registers.md`
### The fault, and how it was found

On 2026-11-03 the constellation road (PR 487) added three doors under `bin/` and regenerated `bin/README.md` —
the register `bin/gates/guards.sh` checks — and not `.agents/assets/agents/capabilities.md`, which only
`bin/gates/ci-verify.sh` checks. `main` went red on that gate at the merge, and **four collaborators' open PRs
then showed a failure that was not theirs**: a red X that reads as their defect, on work that was fine.

The deeper fault is not the two forgotten lines. It is that the house keeps two generated registers, written by
two generators, checked by two gates, named almost the same, and **neither generator tells you the other
exists**. Any hand that adds a file can half-regenerate a tree, and the half it forgot is invisible locally.

### What changed

- **`bin/gates/registers.sh`** — one door with ONE list of generators (`bin/gates/inventory.sh`,
  `bin/gates/capabilities.sh`): `list` · `generate` · `check`. A generator is added there or it runs nowhere.
  A generator that fails is named and the door exits non-zero; it never silently skips one. An empty list
  refuses rather than passing.
- **`bin/gates/guards/registers-guard.sh`** — the ward, seated in `bin/gates/guards.sh`, so a push and CI judge
  the same set instead of two different ones.
- **`bin/gates/tests/test_registers.sh`** — 7 assertions: the list names both generators; a **drifted register is
  detected** (a line appended to a door must make `check` fail, never pass); `generate` then `check` is clean.
- **`docs/features/one-door-for-the-registers.md`** and a FEATURES row.

### The order that works, written where it is needed

`inventory.sh` enumerates **tracked** files, so a register written before `git add` describes a tree without the
new doors and is stale the instant the commit exists — the push gate then fails on a branch where nothing is
wrong. **Write → stage → generate → commit → push.**

### What was proved

`bash bin/gates/tests/test_registers.sh` → 7/7. `bash bin/gates/registers.sh check` → both current.
`bash bin/gates/guards.sh` → every ward PASS, including the new one.

### A second ward was red for everyone, and it was not the change's fault

CI on PR 493 failed on `features-guard.sh` while the same ward passed locally. The cause was not the tree:
the guard required a **per-clone git config** (`merge.regenerate.driver`), which `weave-features.sh --install`
seats. A fresh CI clone has never run that, so **every PR — and `main` itself — failed a ward about a merge
that never happens in CI**.

The driver is *declared* in `.gitattributes` (`FEATURES.md merge=regenerate`), and that file is tracked, so every
clone and CI carry the declaration. The guard now judges the **declaration** plus the presence of
`bin/records/regenerate-on-merge.sh`, and reports a missing per-clone config as a **note**, not a fault:

```
"the merge driver is declared but not seated in this clone","FEATURES.md","run … --install for this clone (CI does not merge, so it is a note here, not a fault)"
```

That is the difference between a ward that guards a behaviour and a ward that guards a workstation. A gate that
fails on every clean tree teaches people to ignore gates — which is the same disease as the register trap this
PR exists to cure.
