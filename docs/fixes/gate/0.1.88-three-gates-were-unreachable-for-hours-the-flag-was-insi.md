## gate · 0.1.88 · 2026-10-02 — three gates were unreachable for hours — the flag was inside the quotes

### Files
- `bin/gates/ci-verify.sh`

## The flag was inside the quotes

Three gates in `ci-verify.sh` read:

```bash
gate queue  "the derived work queue is current"   bash "$ROOT/bin/queue.sh --check"
```

Bash passes **one argument** — the literal string `/home/heimdall/ymir/bin/queue.sh --check` — so
`bash` tried to open a file *named* `queue.sh --check`, and printed:

```
bash: /home/heimdall/ymir/bin/queue.sh --check: No such file or directory
```

**The error message held the answer the whole time** — the flag is *inside the filename*. It
surfaced earlier in the session as an unexplained `ENOENT` on this same line, was written off as
a path/environment mystery, and was in fact one misplaced quote character in each of three lines.
The fix moved the closing quote: `bash "$ROOT/bin/queue.sh" --check`.

**Why it survived so long, and why that is the more useful note:** the gate never ran, so it never
had an opinion — it was permanently red, and a *red gate that is stuck red* reads as "this
environment is broken" rather than "this line is wrong". Nothing in CI distinguishes a gate that
fails from a gate that cannot start. A gate whose command **cannot execute** should say so in one
line rather than be counted as a verdict:

```bash
command -v "${4##*/}" >/dev/null 2>&1 || …
```

**Verified:** all eight `--fast` gates now `PASS` — ward, compliance, contracts, queue,
capability, home-index, usage, inventory.
