## The register, and a check that must never write

`bin/capabilities.sh` writes `.agents/assets/agents/capabilities.md` — **382 door rows**, each with
the job (read from the door's OWN header), the verdict (tested / named / both / neither) and the tech
decision. Its `--check` is wired into `bin/gates/ci-verify.sh` so a stale register fails a gate.

**A register that is authored rots** — that is what happened twice to `register.md` in one evening —
so this one is generated from the tree, and the rule it carries is explicit:

> **if a job is not a row here, no agent may improvise a script for it — an unlisted job is an
> OPEN ROW, not a new `bin/whatever.sh`.**

The uncalled doors are printed in §3 with the two honest answers (add a row, or move the file to
`hodd/reference/` per Rule 11) and never a third.

## Two faults the gate caught in the gates themselves

1. **`bin/queue.sh --check` WROTE the queue before checking it.** The generator ran before the mode
   branch, so a *check* could mutate the very artefact it verifies — in the vault. Fixed: `--check`
   renders to a temp and never touches the queue. **Proven, not assumed:** the queue's md5 is
   identical before and after a `--check`.
2. **The capability register counted `0 doors` while holding 382 rows** — a backtick-escaped grep.
   The count now matches how the rows are actually written.

## Still open, and it is not hidden

Both new gates **pass when run directly and FAIL inside `ci-verify.sh`** with
`bash: …/bin/queue.sh --check: No such file or directory` — an ENOENT for a file that demonstrably
exists and runs with the same invocation. I have not root-caused it, so it is recorded here rather
than declared fixed. Until it is: run the two checks directly, and treat the CI rows as a known
false failure.
