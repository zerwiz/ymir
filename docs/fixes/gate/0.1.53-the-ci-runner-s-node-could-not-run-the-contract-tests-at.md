## gate · 0.1.53 · 2026-09-29 — the CI runner's node could not run the contract tests at all

### Why
With the SKIP mended (see the sibling note), the gates workflow **still** failed — and
the fault was above the type-check, in the one leg that is supposed to need nothing:

```
"tests","FAIL"  →  # tests 1   # pass 0   # fail 1
```

`node --test packages/contracts/test/` runs **TypeScript** test files. Type stripping is
only on by default from **Node 22.18 / 23.6**, and `.github/workflows/ymir-gates.yml`
declared no `setup-node` at all: it inherited whatever `ubuntu-latest` shipped, which
cannot load a `.ts` file. This seat runs Node 26.8.1, so the identical test **passes
here** — the failure was unreachable from any seat, and CI was reporting a fault in
correct code that no author could reproduce or mend.

A gate whose verdict depends on whatever the runner happened to install is not a gate; it
is a coin with a slow reveal.

### Fix
The gates workflow now **pins** the node it runs on:

```yaml
- name: Seat the node
  uses: actions/setup-node@v4
  with:
    node-version: '24'
```

One workflow, one line of intent. The workflow's own doctrine — "One room, two doors …
the checks have exactly one home and cannot drift between hosts" — is honoured: both
GitHub Actions and Forgejo Actions run this same file, so both rooms are seated at once.

`package.json` keeps `engines.node: ">=20"` **on purpose**. That is the floor for a machine
*consuming* the package; this fault is about the floor for *developing and gating* it.
Widening `engines` would narrow who may install Ymir, to fix a CI determinism problem —
the wrong trade.

### Verified
- Workflow parses; steps are now `Checkout → Seat the node → The gates`.
- Locally the same leg passes: `contracts_check` → `tests PASS (pass 4 · a mismatched card
  is refused)` on Node v26.8.1, which is the behaviour CI now reproduces by construction.
- No change to what the gate proves — only to the room it proves it in.

## Correction (2026-09-29, later the same hour) — the node version was NOT the fault

The note above named type stripping as the cause. **That diagnosis was wrong**, and the
record says so rather than being quietly rewritten.

With node 24 actually seated, the tests leg still failed — and printed the truth:

```
Error: Cannot find module '/…/packages/contracts/test'
    at Module._resolveFilename (node:internal/modules/cjs/loader:1164:15)
  code: 'MODULE_NOT_FOUND'
```

**`node --test <directory>` is not a stable contract across node majors.** Node 24
resolves the argument as a module entry point; Node 26 treats it as a directory to search.
The same command passed on this seat and failed in CI for a reason that had nothing to do
with TypeScript, `@types/node`, or the version floor.

### The real fix
Pass the **files**; let the shell expand the glob:

```sh
node --test packages/contracts/test/*.test.ts    # was: node --test packages/contracts/test/
```

Verified on **both** rooms: `pass 4 · fail 0` under Node 24.21.0 and under this seat's
Node 26.8.1. The same correction is applied to `packages/contracts/package.json`'s own
`test` script, which carried the identical latent fault.

### What stands from the original note
- The **`setup-node` pin stays**: not as the fix, but because a gate whose verdict depends
  on whatever node the runner shipped is still a coin with a slow reveal. Determinism is
  worth having whether or not it was the fault.
- `engines.node: ">=20"` **stays** unchanged, for the reason given above.
- The `modules_present` SKIP for the two type-check legs (the sibling note) is unaffected
  and remains correct.
