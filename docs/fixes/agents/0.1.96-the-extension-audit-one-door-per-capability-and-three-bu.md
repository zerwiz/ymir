# 0.1.96 — the extension audit: one door per capability, and three bugs only a runtime finds

> *"are all files in bin in some extention now? we may need to split extension up or move some
> tool calls to others. we need to make a audit"*

**Measured answer: `31 of 392` bin doors are reachable from a tool — and that is the design.**
Wrapping every door would break the law that made this house work: **one capability, ONE
registered tool**. The test is *"would I, mid-conversation, ask for this?"* A cron row cannot call
an MCP tool and a human types a door, so those stay doors.

## A correction to the audit itself

The audit reported that `rules` and `odrerir` **overlap on four doors** (`queue`, `capabilities`,
`inventory`, `verify-seat`). That was **wrong**, and the correction matters more than the finding:

`rules.ts` **names** those gates in its help text; it never executes them. It reads `ci-verify.sh`
as *text* to list the gates and nothing else. `odrerir` is the one that runs them. The separation
was already correct.

So the fix for a finding that was never real is **not a refactor** — it is deleting an unused
import (`execFileSync`, imported and never called) and saying so out loud. A wrong finding costs
exactly as much as a right one if it is acted on.

## Three bugs the audit found by LOOKING, not by reading

### A literal bash never expands

```ts
run("bash", ["${YMIR_HOME:-$HOME/Documents/ymirhome}/bin/calendar-ask.sh", "free"], HOME)
```

Bash does not expand a variable inside an argument **it was handed**. So the calendar tool had
**never once reached the calendar on any seat** — and nothing noticed, because *a broken tool and
an absent tool look identical from the outside*.

### Five extensions carried a hardcoded `/home/heimdall/ymir`

Rule 07, and I introduced it. The contract now: `YMIR_ROOT`, else the root
`bin/valknut-load.sh` records in `~/.pi/agent/extensions/.ymir-root` — **the first recorded root
that really holds `bin/syn-watch-arm.sh`** — else a failure that names the fix. Two details that
cost me a cycle each: the pointer lives **inside** `extensions/`, not one level up, and a root may
be a **list**, because a worktree seat is recorded beside the main one.

### `join` imported from `node:fs`

A type-stripping parser accepts it. esbuild accepts it. **Only the runtime refuses it** — `join` is
in `node:path`. Nine files. Found by a smoke test that *loads* every extension:

```
elder: 5 · ymirhome: 11 · managandr: 1 · eir: 2 · opendesign: 1 · odrerer: 1
```

**A parse-only check would have shipped all nine.**

## And the ward now reads `.pi/`

`defaults-guard.sh` scanned `bin/ .agents/ tools/ scripts/ src/` and **not `.pi/`** — where every one
of those bugs lived, in runtime code, unguarded. Adding `.pi/` surfaced **five more real findings on
the first run**: three `${process.env.HOME}/Documents/ymirhome` guesses, the unexpanded literal,
and a `$YMIR_HOME` guess. All fixed; clean.

**One item left open, named rather than quietly dropped:** `ymir_recall` / `ymir_remember`
(`ymirhome`, via `bin/mimir.sh`) and `well_recall` / `well_observe` (`ymir-well`, in-process) are the
**same capability twice**. The `mimir.sh`-backed pair is the correct shape — a thin door a human can
also run — but `ymir-well` ships and predates this work, so removing a shipped tool is a larger
decision than an audit should make silently. **Recommendation:** keep `ymir_recall`/`ymir_remember`,
retire `ymir-well`'s pair into `hodd/reference/` with the reason (Rule 11).
