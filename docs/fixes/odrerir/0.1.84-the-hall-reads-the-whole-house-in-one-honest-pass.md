## What it is, and what it refuses to be

> *"functional with odrerir the app"* — the hall had no single honest read of what the house is
> doing, so the app (or a reader) reached into five doors and reconciled them by hand.

`ymir_hall` is **ONE tool** and it writes nothing. Every figure comes from the door that owns it —
the seat from `bin/seat/verify-seat.sh`, the counts from the register, the tally from the derived queue,
the verdicts from `bin/README.md`, the last entries from the runes ledger — so **the hall cannot show
a number the tree does not hold.**

**The law it carries:** *a door that could not answer is shown UNABLE, never as zero.* An absent
answer is not an empty one — and that distinction is the same one `ymir_dellingr` and
`ymir_header` are built on.

## Two defects its own first run exposed

1. **It printed `? ? ? ?`** for the door counts — because the register had lost its
   `capabilities[5]` headline in a heredoc edit of mine. Fixed in the *writer* (see the gate note
   0.1.83), and the counts now read `shell 389 · engine 54 · skills 29 · tools 33`.
2. **It reported the queue as UNABLE** — it required exit 0 and a long render, so a working door
   looked broken. A door that answers slowly is not a door that failed; the read now takes the tally
   from the output rather than from the exit code.

**That both happened on the FIRST run, in a tool built to summarise other tools, is the finding.**
A surface that reports on the house must be the most boring thing in it, or it becomes the
noisiest.
