## What was wrong, on nidavellir, 2026-11-05

`runtime-pinned-guard.sh` failed on **five** units — bifrost, mcp-gateway, mimir, nornir, ymir-syn-watch — because each `ExecStart` named
`/home/zerwizomar/ymir/bin/...`: **the working tree**. The guard's own help says *"point those units at ~/ymir-runtime
(bin/engine/runtime-deploy.sh does the move and proves it)"*, and that was wrong in one respect: `runtime-deploy.sh` moves and proves the
**checkout**, but nothing repinned the **unit files**.

So on a seat whose units had been rendered the old way, every push was refused and no door could fix it. `fleet-ensure.sh` renders these units with
`__YMIR_BIN_DIR__ = $ROOT/bin` and never consulted `YMIR_RUNTIME_DIR` — the four-line secret of why the ward could never go green.

## The change

`bin/fleet/fleet-ensure.sh` now resolves the pin **once**, in this order: `$YMIR_RUNTIME_DIR`, then `YMIR_RUNTIME_DIR` from
`$YMIR_HOME/config/runtime.env`, with an unexpanded `$HOME` resolved. If that path is a real checkout holding `tools/mill/systemd`, it **is**
`FLEET_TEMPLATE_ROOT`, and the units are rendered against it. If the pin is configured but unusable, the door **says so on stderr and names the
working tree it is falling back to**, because a silent fallback is the fault this whole ward exists to catch.

## Proved

- `bin/gates/guards/runtime-pinned-guard.sh` → **`"none","every unit names /home/zerwizomar/ymir-runtime, and it stands on main"`**.
- `bin/fleet/fleet-ensure.sh ensure` → every role-owed program re-rendered, enabled and standing; `ymir.target` enabled.
- `bin/engine/runtime-deploy.sh` → `deployed e3b182f6, every unit settled`.
