## runtime · 1.0.5 · 2026-11-08 — the apps run from a release behind one symlink, and an update never moves under an open window

### Files
- `bin/engine/release-lib.sh` — the one place that knows where a release lives, how a commit is
  abbreviated, and how a symlink is swapped in one rename.
- `bin/engine/release-build.sh` — forge an immutable release from a commit.
- `bin/engine/release-health.sh` — can *that directory* serve the apps?
- `bin/engine/release-flip.sh` — health first, then one rename, then a watch window.
- `scripts/{start,electron,raise}.sh` — each answers `--root`: where it thinks the tree is.
- `docs/features/atomic-releases.md` — the how-to; its catalogue row.
- `FEATURES.md` — re-woven from the fragments.

## What was wrong

The runtime **is the tree the process was started from**, and that tree is where hands
and agents check branches out. On 2026-11-08 five desktop entries were found pointing
into a worktree that a session deletes when the errand ends, and two of them had no
Electron at all. The launcher was fixed the same hour (the entries now read the canonical
checkout), but the launcher was only the visible half: `scripts/start.sh` raises fifteen
services from `$ROOT`, and `$ROOT` moves whenever the code moves. An update therefore
reached straight into a running hall.

Plan 221 named the shape that ends this: an update produces a new **immutable release**,
a single symlink names the live one, the flip is **atomic and health-checked**, a running
app keeps the release it started in until it is restarted, and a rollback is flipping the
link back. P0–P2 are those three doors; nothing points at the symlink yet (that is P3).

## The change

**`release-build.sh <sha>`** exports the commit with `git archive | tar -x` into
`~/ymir-releases/<12-char-sha>/`, **resolves every symlink into a real file** (`config/`
is a link into `.agents/config`; the harness dirs are links into `.agents/`), installs
the dependency closure **inside** the release, builds the assets **inside** it, writes a
manifest naming its own sha, and links the release to a **shared shelf** (`~/ymir-shared`:
state, logs, pids, the hoard, the vault) so the release writes nothing of its own. A link
whose target escapes the release is a **refusal**, not a copy. It builds into a temporary
name and renames it into place — the same "stage, then activate" law as the flip.

**`release-health.sh <dir>`** proves the directory is a release, that its manifest tells
the truth, that nothing dangles or escapes, that the release's **own** `scripts/electron.sh`,
`start.sh` and `raise.sh` resolve the root *to the release* (each answers `--root`, so the
script is asked rather than the caller recomputing the answer), that the dependency closure
and the SPA build exist, that `bin/desktop/desktop-verify.sh` finds a runnable Electron
**under it**, and that the four services answer **from that directory** — attributed by the
serving pid's cwd and by the root the gate itself reports. `--live` additionally raises the
release's own gate, SPA, visualizer and hall on probe ports (canonical + 10000) and proves
each answers before stopping them.

**`release-flip.sh <sha>`** asks health first and does not move the link on a refusal, then
swaps with `ln -s <release> <link>.tmp && mv -T <link>.tmp <link>` — **one rename, and never
a `rm` before the `ln`** (plan 221 §10: a delete-then-create leaves a window where nothing
is current, and that is a phase failure, not a style note). It records every act in
`~/.local/state/ymir/releases.log`, and if the release it just made live degrades inside its
check window it **flips back on its own** and records `result=rolled-back` with the reason.

Retention is three releases, pruned **by age before a build** and never after a failure, so
a failed build never costs the release you would roll back to. Nothing is forced, reset,
stashed or cleaned; the desktop entries, the units, the running apps and the hoard are not
touched; no container runtime is involved (that is P5, and this machine has none).
