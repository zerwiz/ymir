## runtime · 1.0.5 · 2026-11-08 — the apps run from a release behind one symlink, and an update never moves under an open window

### Files
- `bin/engine/release-lib.sh` — the one place that knows where a release lives, how a commit is
  abbreviated, and how a symlink is swapped in one rename.
- `bin/engine/release-build.sh` — forge an immutable release from a commit.
- `bin/engine/release-health.sh` — can *that directory* serve the apps?
- `bin/engine/release-flip.sh` — health first, then one rename, then a watch window.
- `scripts/{start,electron,raise}.sh` — each answers `--root`: where it thinks the tree is.
- `docs/features/atomic-releases.md` — the how-to; its catalogue row.
- `FEATURES.md` — re-woven from the fragments.

## What was wrong

The runtime **is the tree the process was started from**, and that tree is where hands
and agents check branches out. On 2026-11-08 five desktop entries were found pointing
into a worktree that a session deletes when the errand ends, and two of them had no
Electron at all. The launcher was fixed the same hour (the entries now read the canonical
checkout), but the launcher was only the visible half: `scripts/start.sh` raises fifteen
services from `$ROOT`, and `$ROOT` moves whenever the code moves. An update therefore
reached straight into a running hall.

Plan 221 named the shape that ends this: an update produces a new **immutable release**,
a single symlink names the live one, the flip is **atomic and health-checked**, a running
app keeps the release it started in until it is restarted, and a rollback is flipping the
link back. P0–P2 are those three doors; nothing points at the symlink yet (that is P3).

## The change

**`release-build.sh <sha>`** exports the commit with `git archive | tar -x` into
`~/ymir-releases/<12-char-sha>/`, **resolves every symlink into a real file** (`config/`
is a link into `.agents/config`; the harness dirs are links into `.agents/`), installs
the dependency closure **inside** the release, builds the assets **inside** it, writes a
manifest naming its own sha, and links the release to a **shared shelf** (`~/ymir-shared`:
state, logs, pids, the hoard, the vault) so the release writes nothing of its own. A link
whose target escapes the release is a **refusal**, not a copy. It builds into a temporary
name and renames it into place — the same "stage, then activate" law as the flip.

**`release-health.sh <dir>`** proves the directory is a release, that its manifest tells
the truth, that nothing dangles or escapes, that the release's **own** `scripts/electron.sh`,
`start.sh` and `raise.sh` resolve the root *to the release* (each answers `--root`, so the
script is asked rather than the caller recomputing the answer), that the dependency closure
and the SPA build exist, that `bin/desktop/desktop-verify.sh` finds a runnable Electron
**under it**, and that the four services answer **from that directory** — attributed by the
serving pid's cwd and by the root the gate itself reports. `--live` additionally raises the
release's own gate, SPA, visualizer and hall on probe ports (canonical + 10000) and proves
each answers before stopping them.

**`release-flip.sh <sha>`** asks health first and does not move the link on a refusal, then
swaps with `ln -s <release> <link>.tmp && mv -T <link>.tmp <link>` — **one rename, and never
a `rm` before the `ln`** (plan 221 §10: a delete-then-create leaves a window where nothing
is current, and that is a phase failure, not a style note). It records every act in
`~/.local/state/ymir/releases.log`, and if the release it just made live degrades inside its
check window it **flips back on its own** and records `result=rolled-back` with the reason.

Retention is three releases, pruned **by age before a build** and never after a failure, so
a failed build never costs the release you would roll back to. Nothing is forced, reset,
stashed or cleaned; the desktop entries, the units, the running apps and the hoard are not
touched; no container runtime is involved (that is P5, and this machine has none).

## Proved

Every line below was measured on this machine, on a real release pair — two releases forged
from two commits, flipped, degraded and rolled back. Commands are quoted exactly.

**A release whose own scripts resolve inside it.**

```
$ bin/engine/release-build.sh HEAD
release-built[1]{sha,dir,size,files,deps,electron,assets,symlinks,own_root}:
  "583059cc321b","~/ymir-releases/583059cc321b","587M",5114,"installed via npm install","mended","hlidskjalf odrerir",127,"~/ymir-releases/583059cc321b"
$ bash ~/ymir-releases/583059cc321b/scripts/electron.sh --root
~/ymir-releases/583059cc321b
$ bash ~/ymir-releases/583059cc321b/scripts/start.sh --root
~/ymir-releases/583059cc321b
$ bash ~/ymir-releases/583059cc321b/scripts/raise.sh --root
~/ymir-releases/583059cc321b
```

127 symlinks were materialised into real files (`config/` → `.agents/config` among them); the
release links `shared`, `.run`, `state` and `logs` to `~/ymir-shared` and writes nothing of its own.

**The services answer FROM that directory** (`--live`; the hall's own services were never disturbed
— the probes run on canonical + 10000):

```
"service:gate","ok","answered :13889/api/health from ~/ymir-releases/583059cc321b/apps/hlidskjalf (pid 195314)"
"service:gate-root","ok","the gate names ~/ymir-releases/583059cc321b as the tree it serves"
"service:spa","ok","answered :13888/ from ~/ymir-releases/583059cc321b/apps/hlidskjalf (pid 195664)"
"service:visualizer","ok","answered :18437/api/health from ~/ymir-releases/583059cc321b/apps/smidja-factory/apps/visualizer (pid 196292)"
"service:hall","ok","answered :14322/ from ~/ymir-releases/583059cc321b/apps/odrerir (pid 196653)"
```

and `desktop-verify` inside the release: `"desktop","ok","every surface resolves a runnable Electron
and is routed right"`.

**A deliberately broken release is REFUSED, and the link does not move.** The first release built
today shipped no Electron binary (npm 11+ gated the postinstall; `install.js` exits 0 and leaves only
`locales/`), which is exactly the half-built release this door exists to catch:

```
$ bin/engine/release-flip.sh ~/ymir-releases/10f78116686b
  "desktop","FAIL","no executable Electron runtime — the resolver found nothing under …/apps/hlidskjalf"
  "refused","10f78116686b did not pass its health check — ~/ymir-current was not touched"
$ readlink ~/ymir-current      # before and after: unset
```

The mend that followed (run Electron's own installer inside the release, then the cache-then-network
zip road) is what the build now does; a release that still cannot land the runtime is `electron:
absent` in its manifest and refused here.

**The flip moves the link in ONE rename, and the previous release still runs.** A poller read
`readlink ~/ymir-current` every 10 ms across the flip: **1011 samples, 0 absent**, and only two
distinct values — the old release, then the new one. Nothing was ever current-less.

```
"583059cc321b","still on disk and still healthy — rollback is one rename"
```

**A rollback was actually performed, and the log says so.** The second release was flipped with a
25-second window; one second after the link named it, its `apps/hlidskjalf/dist` was moved aside (a
real degradation: the SPA has nothing to serve). The door caught it inside the window, flipped back
on its own, and recorded why. The poller across the whole act: **2338 samples, 0 absent**, values
`583059cc321b → 50ba9256befc → 583059cc321b`.

```
2026-11-08T20:38:37Z  flip  from=50ba9256befc to=583059cc321b health=degraded window=25s result=rolled-back reason="assets","FAIL","apps/hlidskjalf/dist/index.html is absent — the SPA has nothing to serve";
```

`release-flip.sh` exited 1 and named the rollback; the release was restored and re-checked healthy
afterwards, so the shelf was left honest.

**Skips, stated plainly rather than pretended.** The Smíðja visualizer's own build is skipped in the
release (`smidja-visualizer(build failed)`) and `scripts/start.sh` builds it on first raise, as it
always has. Without `--live`, the four canonical ports are reported as served by `~/ymir` — that is
the P3 world, and the row says so instead of counting it as proof. No container runtime exists on
this machine, so no container step was attempted (P5).
