# 0.1.107 — nobody ran the session-start door, and 1595 lock orphans never cleared

> *"fix that also so it works"* — closing the last gap I had named: that a queued wake reaches a
> **newly opened** session.

## What was actually broken

`bin/time/saga-session-start.sh` drains the wake queue, seeds the digest and raises the bridge. It works
perfectly — I ran it by hand:

```
wake queue: 1 pending
WAKE eindri constellation-pi reported: report filed at …/constellation-pi.md
exit 0
```

**And a wake had been sitting in `state/.wake-queue` since 2026-10-01, undrained.** Because:

> **No extension ever EXECUTED that door.** Four of them *mention* it — in a comment, in a help
> string, in an error message — and none called it. `session_start` armed the watch and did nothing
> else. So the queue was durable, the drain worked perfectly when a human reached for it, and the
> delivery half of supervision was simply **not wired to anything**.

This is the same shape as the previous two fixes, one level out: the ownership rule asked about a
pid instead of a supervisor; this asked **whether the door worked** instead of **whether anything
called it**.

## The fix

`session_start` now seats the session — it runs the door, which drains the queue and seeds the
context, so a fresh window opens knowing what was waiting for it. **Best-effort and never fatal**: a
session that cannot seat is still a session. But a failure is **shouted**, because *"the door
failed"* and *"the door was never called"* look identical from outside — the exact distinction the
watcher check learned the hard way in 0.1.103.

## Second finding: 1595 orphans, and a prune that reported nothing wrong

`state/` held **1,595** `wake-queue.lock.steal.owner.*` directories, 14 MB. One per lock-steal
attempt: `fm_lock_discard_owner` cleans up a **failed** claim, and a claim that *succeeds* leaves its
directory behind for ever. Nothing ever asked what the right number was.

`fm_lock_prune_orphans` now runs on every claim and removes only directories that **no lock symlink
points at** and that are **older than a minute** — a live lock's owner directory can never be
pruned, because the test *is* the symlink.

```
1595 → 0 orphans        state/ 14M → 11M
```

### And the prune had the same bug I have been fixing all night

My first version guarded on `[ -d "$lockdir" ]`. **The lock is a symlink to a FILE, not a
directory** — so the guard was false, the function returned immediately, and it pruned *nothing*
while reporting no error at all. The residue looked untouched, which was the honest signal.

Proved both directions after fixing it:

```
live lock's owner dir still there?  YES — correct, never pruned
symlink intact?                     yes
unreferenced orphan pruned?         YES
```

> A cleanup that cannot fail is not a cleanup. **Measure the effect, not the exit code** — which is
> the ninth member of this family, and the one that finally bit me in my own new code.
