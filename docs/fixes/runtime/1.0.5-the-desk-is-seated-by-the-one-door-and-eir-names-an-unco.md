## runtime · 1.0.5 · 2026-11-05 — the desk is seated by the one door, and Eir names an unconfigured desk

### Files
- `bin/fleet/fleet-ensure.sh`
- `bin/engine/autoboot-lib.sh`
- `bin/agents/eir-doctor.sh`
- `bin/desktop/ymir-style.sh`
- `tools/mill/systemd/gna-desk.service`
- `config/cron.yaml.example`
### Why

The desk stood because a hand once ran `bin/mail/install.sh` on one machine. It was in no role's
owed list, so `bin/fleet/fleet-ensure.sh ensure` never rendered it, `ymir.target` never pulled it at
boot, and `bin/agents/eir-doctor.sh` had nothing to say about it. A capability that only a hand can
raise is a capability the fleet does not have — and a desk that answers with *no account* answers
exactly like an empty inbox, which is the one lie this house keeps paying for.

### Fix

- **One door seats it.** `gna-desk` joins the role-owed table (`bin/engine/autoboot-lib.sh`): owed by
  `heart`, `forge` and `dev`, joined to `ymir.target`, described in one line like every other program.
  `tools/mill/systemd/gna-desk.service` is a TEMPLATE, and `materialize_web_unit` renders it.
- **Rendered against the PINNED RUNTIME, not the working tree** (RULES/02 §7). `__YMIR_BIN_DIR__` now
  resolves from the home's `config/runtime.env` (`YMIR_RUNTIME_DIR`, default `~/ymir-runtime`) when that
  checkout stands, and only falls back to the main tree where no pinned runtime exists. Ten units were
  re-pointed at `~/ymir-runtime` by hand on 2026-11-02; from here the renderer does it. The proof is the
  ward: `bin/gates/guards/runtime-pinned-guard.sh` reports `every unit names /home/zerwizomar/ymir-runtime`.
- **ARMED ONLY WHERE AN ACCOUNT IS DECLARED.** `mail_accounts_declared` reads the account rows out of
  `$YMIR_HOME/hodd/memory/mail/accounts.yaml`; with no row the ensure prints
  `gna-desk — NOT ARMED: no account row in …/accounts.yaml`, drops the program from the raise, and arms
  nothing. The same gate guards the `unit gna-desk` render and the raise itself, so no path can seat an
  unconfigured desk.
- **Eir names three truths** (`bin/agents/eir-doctor.sh`): `ok` (the desk answers `/health` with a
  declared account), `unconfigured` (it answers, and has no account — a NAMED, non-green state, counted
  apart from `broken` and exited non-zero), `broken` (no answer). The detail names the account, and the
  three vault KEY NAMES when the declared grant's keys are absent. The mend is `bin/mail/install.sh`;
  the ACCOUNT is the operator's word and is never mended. `unconfigured` also carries its own mark in
  `bin/desktop/ymir-style.sh` (`?`, bronze — it asks for a name, it is not a fault of the code).
- **The ruled digest rhythm** is written where a seat copies it: `config/cron.yaml.example` carries six
  commented rows — every two hours, 07:20–17:20 — with the law that each run is INCREMENTAL (the
  notification ledger decides what is new; the window never re-reads a week).

### A fault found on the way

`materialize_web_unit` wrote the unit and *then* refused a disposable path. Run from a Yggdrasil worktree
it therefore wrote `apps/…/.yggdrasil/…` into `hlidskjalf-spa`, `hlidskjalf-gate` and `smidja`, printed
REFUSED, and left the seat running a path it had just called unlawful (measured 2026-11-05, this errand).
It now renders beside the unit, refuses there, and only then moves it: a refused render leaves the
PREVIOUS unit standing. Re-run from the worktree, the three refusal lines print and not one unit changed.

```

{"ok": true, "read_only": true, "send_capability": "none", "accounts": ["<the operator's own mailbox>"], …}

$ bin/agents/eir-doctor.sh check | grep '"mail"'
  "mail","ok","desk answers for <the operator's own mailbox> at http://127.0.0.1:8490"

$ bin/gates/guards/runtime-pinned-guard.sh
  "none","every unit names /home/zerwizomar/ymir-runtime, and it stands on main"
```

Both non-green states were exercised, not assumed: a desk on :8499 with `accounts: []` reports
`"mail","unconfigured","the desk answers, but no account row in … — nothing to read, and "no mail"
cannot be said"` (exit 1), and an account row naming three absent keys reports `… the declared grant
names vault keys that are ABSENT: NOT_A_REAL_GRANT_KEY NOT_A_REAL_CLIENT_ID NOT_A_REAL_CLIENT_SECRET`.
The unconfigured gate was exercised against a home with no scope file:
`fleet: gna-desk — NOT ARMED: no account row in /tmp/fakehome-empty/hodd/memory/mail/accounts.yaml`,
and `gna-desk` did not appear in the raise.
