# 0.1.125 — the hand's well door: an SSH forward that reports what is behind it

## What the measurement showed

`well_recall` on the phone: *"the well did not answer (0): fetch failed"*. Nothing listened on
`127.0.0.1:4602`, and `bin/agents/eir-doctor.sh` reported **`well ok`** — a green row produced by
the presence of two scripts, not by the well.

Measured across the fleet with `bin/records/well-door.sh status`:

```
well-door[zerwizserver]{port,here,heart}:
  "4602","forward up, but NOTHING behind it","nothing listening on the heart"
  "8317","answering","LISTEN 0 2048 0.0.0.0:8317 0.0.0.0:*"
```

So the fleet today speaks **engram-mcp over :8317** on the heart; the HTTP face the repo's
`mimir.sh` expects (`bin/bridge/mimir-bridge.py`, :4602) is **not running there at all** — and the
heart's checkout cannot start it either: `~/ymir` on `zerwizserver` is `ahead 1021, behind 1536`,
from before the `bin/` restructure, and has no `bin/records/`.

## The fix (the door half)

`bin/records/well-door.sh` — the hand's door to the heart's well, over SSH:

| verb | what it does |
|---|---|
| `up` | raises `-L 127.0.0.1:<port>:<behind>:<port>` for each port that is not already up |
| `down` | closes exactly those forwards |
| `status` | probes **both ends** and names the truth: `answering` · `not raised (heart listens)` · `forward up, but NOTHING behind it` · `silent both ends` |

The four states exist because a forward that is up proves only that `ssh` is up. The first draft
of this script called `4602` "answering" the moment the forward accepted a connection — the same
false green Eir had. Both ends are asked now, and the heart's own `ss` line is printed beside it.

## The half that is NOT mended, and why

The memory itself is unreachable by the HTTP road until one of these is chosen:

1. **Migrate the heart's checkout** (`ahead 1021 / behind 1536` — its local commits may be
   precious; this is the Allfather's decision, not an agent's), then
   `bin/records/mimir.sh start` there; or
2. **Move the phone's well client to MCP** — the forward to `:8317` already answers, so the
   remaining work is a stdio→HTTP MCP shim (`mcp-remote`) in the Pi/OpenCode MCP config.

Until then `well-door.sh status` reports `4602 · forward up, but NOTHING behind it`, and Eir's
`well` row is red with that reason — which is the honest state of the fleet.

## Verified

```
well-door.sh up     → raised 2 forward(s) to zerwizserver
curl 127.0.0.1:8317/sse → 200 (the heart's engram-mcp answers through the door)
well-door.sh status → 8317 answering · 4602 "forward up, but NOTHING behind it"
eir-doctor.sh check → well → broken, "door silent on :4602 (role hand: the well is the heart door)"
```
